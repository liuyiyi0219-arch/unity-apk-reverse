# 7.2　AssetBundle 破部分加密

> 状态：🟢 已完成（正文 + 真加密 AB 靶，UnityPy 真跑）｜第七部分（资源 / AB）

---

## 一、本章的目的

7.1 是**裸 AB**——丢进工具点导出。这一课是另一半：**AB 被加密**了。加密后标准工具（AssetStudioMod / UnityPy）**读不出里面的对象**——不是报错，而是 **exit 0 + 导出 0 个文件**（容器目录被盖住、找不到 block）。这一课讲**加密怎么设计的、为什么只加一小段就够狠**，然后动手把一个加密 AB **解开、提出里面的资源**。

> **和 7.1 一样的动手模式**：7.1 从裸 AB 提一张带 flag 的图；这一课 flag 也埋在 AB 里的一张图上——但 AB 加密了，**得先解密才提得到那张图**。

---

## 二、为什么是"部分加密"（本章核心）

先看 UnityFS 容器的三段结构：

```
① header       魔数 UnityFS\0 + version + 引擎版本串 + size + ci/uiBlockSize + flags（低 6 位=压缩类型）
② BlocksInfo   ★目录：每个 block 的压缩/大小 + 每个资产的 path/offset（LZ4 压缩的一小段，几十~几百字节）
③ block 数据   真正的资源字节（LZ4/LZMA 压缩），占全文件 90%+ 体量
```

解析器**必须先读懂 header + BlocksInfo**，才知道每个 block 在哪、多大、怎么解压。这一小段是打开整个容器的**唯一钥匙孔**。

**AB 在运行时按需加载，全量解密吃帧率。所以商业方案几乎都不做整包对称加密**，而是——

> **只加密 header 前段（含 magic）**，通常几十字节。标准解析器一上来读 header，magic/字段一乱就**直接读不出对象**——而 90%+ 的 block 数据一字节没动。

**小代价、大杀伤**：加密面积可小到几十字节、运行时解密开销几乎为零；但只要盖住那个钥匙孔，通用工具就瞎了（本章靶子实测：加密 64 字节，占全文件 **0.3%**，UnityPy 就提出 0 个对象）。这就是部分加密的精髓，也是它比整包加密更常见的原因。

## 三、破法：认出加密段 → 恢复 key → 解密 → 提资源

### 第 1 步 · 认出被加密

`xxd` 头 8 字节：明文 AB 是 `55 6E 69 74 79 46 53 00`（`UnityFS`）。**不是**它 → 头被加密了。（直接 UnityPy 载入也会**提出 0 个对象**——头被盖住、解析器进不去。）

### 第 2 步 · 恢复 key（本靶：known-plaintext）

加密段盖住了 header 前段（含 magic）——**magic 本该是 `UnityFS\0`，这就是一段已知明文**。把密文头和已知明文逐字节 XOR，重复的 key 就露出来了：

```
cipher[0..8]  XOR  "UnityFS\0"  →  重复出现的 4 字节 = XOR key
```

> 真实主流方案的 key 常是 **build-time 常量**（编进 `libil2cpp.so`、全端同一把、不依赖设备）→ **静态可解**（强度只算 3 分）。加密没盖住 magic 时就没有 known-plaintext 这个把手，得靠别的线索找 key——但思路一样：**找 key、解那一小段、回去提资源**。

### 第 3 步 · 解密加密段 → 提资源

用恢复的 key 把加密段 XOR 回去 → header 变回明文 → UnityPy 正常读整个容器 → 提出里面的贴图（block 数据一直没动，解密后照常解压）。

### 第 4 步 · 认几套方案的公开指纹

| 方案 | 定位 | 公开指纹 | 强度 |
|---|---|---|---|
| **一种主流官方方案** | AB 加密里的主流（实测约 4.3%） | `libunity.so` 里固定签名常量串；加密打在 header 一小段 | **3 分**：key build-time 常量、静态可解 |
| **第三方加固** | 加固套件可选模块 | `.unity3d` 带附加标记字节 + 专有 native `.so`（RC4 一类） | 中 |
| **自研容器** | 自定义封装 | 非标准魔数；公开解析器 `Escartem/AnimeStudio` 已实现 | 高 |

> 判加密**先 `xxd` 验明文 UnityFS**，以 header 为准（`EE DD` 在压缩数据里随机撞概率极高、不作指纹；从设备拉 bundle 用 `adb pull`/`exec-out` 二进制安全，`adb shell "su -c cat"` 会 CRLF 转换破坏二进制、伪装成加密）。

---

## 四、检查点

- 能说清 UnityFS 三段结构，指出加密通常打在 header 这一小段、为什么打这里最划算。
- 能说清**为什么是部分加密不是整包**：AB 运行时按需加载、全量解密吃帧率 → 只加密钥匙孔一小段，小代价大杀伤。
- 会认出加密 AB（`xxd` 头非 `UnityFS` / UnityPy 提出 0 对象），用 known-plaintext（magic=`UnityFS\0`）恢复 XOR key、解密、提资源。
- 知道主流方案 key 是 build-time 常量、静态可解（不依赖设备）；加密没盖 magic 时换别的线索找 key，思路不变。

## 小结 & 下一章

加密 AB 的破法：**认出加密段 → 恢复 key → 解密那一小段 → 回到 7.1 提资源**。加密几乎都是**部分加密**（只盖 header 钥匙孔，因为运行时性能不能整包解）；本靶的加密段含 magic，用 known-plaintext 就把 key 捞回来了。下一课 **7.3** 转到策划数值（type-tree 解 SO，和美术资源正交）。
